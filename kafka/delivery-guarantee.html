Kafka 유실 · 중복 · exactly-once

메시지가 프로듀서에서 외부 저장까지 가는 동안 어디서 사라지고 어디서 두 번 남는지, 각각 무엇으로 막는지.

1전달 보장과 유실 · 중복 지도

유실부터 막아 at-least-once를 만들고, 그래서 남는 중복을 없애 exactly-once로 간다.

전달 보장 세 단계

보장뜻만드는 법
at-most-once
  • 유실 가능
  • 중복 없음
  • 재시도 없음
  • 처리 전에 커밋
at-least-once
  • 유실 없음
  • 중복 가능
  • 재시도
  • 처리 후에 커밋
exactly-once
  • 결과가 한 번만 남음
  • at-least-once + 멱등
  • 또는 원자적 커밋 (트랜잭션)

어디서 생기나

구역유실중복
1. 프로듀서
  • 재시도 실패를 버림
  • DB 커밋 뒤 send() 전에 죽음
  • 응답을 못 받아 재전송
2. 브로커
  • 복사 전에 리더가 죽음
  • unclean 선출
  • 복제본이 동시에 죽음
  • 없음
3. 컨슈머
  • 처리 전에 커밋
  • 읽기 전에 보존 기간이 지남
  • 처리 후 커밋 전에 죽음
  • 리밸런스
  • 구역마다 유실을 막는 개념 → 중복을 막는 개념 순서로 본다

2프로듀서

유실은 콜백 에러 처리와 outbox로, 중복은 멱등 프로듀서로 막는다.

콜백 에러 처리

  • 무슨 일이 생기나
    • send()는 버퍼에 넣고 바로 반환. 반환됐다고 저장된 게 아님
    • 재시도가 delivery.timeout.ms(기본 120초) 안에 끝나지 않으면 실패로 끝나고, 이 실패는 콜백 · Future로만 알 수 있음
    • 콜백에서 로그만 찍고 넘어가면 그 레코드가 없어진 걸 아무도 모름
  • 막는 법
    • 콜백에서 재처리 큐에 넣거나, 앱을 멈추고 원천에서 다시 읽게 함

outbox

  • 무슨 일이 생기나
    • DB 커밋과 send()는 한 번에 성공하지 않음
    • DB 커밋 뒤 send() 전에 죽으면 주문은 있는데 이벤트는 사라짐
  • 막는 법
    • 이벤트를 Kafka 대신 같은 DB의 outbox 테이블에, 업무 데이터와 한 트랜잭션으로 씀
    • 별도 릴레이가 outbox를 읽어 Kafka로 보냄
  1. 한 트랜잭션으로 기록
    • 주문 INSERT와 outbox INSERT를 같은 트랜잭션에서 COMMIT
    • 둘 다 남거나 둘 다 없음 → 주문과 이벤트가 어긋나지 않음
  2. 미발행 행 읽기
    • 릴레이가 아직 안 보낸 행을 읽음 (주기적으로 조회하는 폴러, 또는 DB 변경 로그를 읽는 CDC)
  3. Kafka로 보냄
    • 키 = 주문 id → 같은 주문의 이벤트는 같은 파티션에 순서대로
  4. 발행 완료 기록
    • 성공 응답을 받은 뒤에만 보냈다고 기록
    • 3번 뒤 4번 전에 죽으면 다시 보냄 → 중복은 받는 쪽 inbox가 event_id로 거름

멱등 프로듀서

  1. seq 7 보냄
    • 프로듀서는 시작할 때 브로커에게 PID(producer id)를 받음
    • 파티션마다 배치에 0부터 1씩 느는 seq를 붙여 보냄
    • 브로커는 (PID, 파티션)별로 마지막 seq를 기억
  2. 응답 유실
    • 로그에는 저장됐지만 응답이 네트워크에서 사라짐
    • 프로듀서는 실패로 알고 재전송
  3. seq 7 재전송
    • 브로커가 이미 받은 seq임을 보고 저장하지 않고 성공만 응답
  4. 멱등 끄면
    • 번호가 없어 브로커가 구분 못 함 → 같은 레코드가 두 번 저장
경우막나이유
같은 프로듀서 인스턴스의 재전송막음
  • 같은 PID · 같은 seq
재전송 중 순서 뒤바뀜막음
  • seq가 비면 브로커가 거절하고 다시 받음
  • 그래서 max.in.flight.requests.per.connection 5 이하에서 순서 유지
앱 재시작 후 같은 데이터를 다시 보냄못 막음
  • 재시작하면 새 PID를 받음
  • outbox 재발행도 여기에 해당 → inbox로 거름
앱이 같은 데이터를 두 번 send()못 막음
  • seq가 다르게 붙음
여러 파티션에 걸친 원자성못 막음
  • seq는 파티션별
  • 여러 파티션을 한 번에 → 트랜잭션
  • 트랜잭션 없는 프로듀서의 PID 상태는 브로커가 producer.id.expiration.ms(기본 1일) 동안 기억

3브로커

"성공 응답을 받은 레코드는 사라지지 않는다"를 복제로 보장한다. 브로커에서는 유실만 생긴다.

ISR과 HW

  • ISR
    • 리더와, 리더를 따라잡은 팔로워의 집합. 리더는 ISR 안에서만 새로 뽑힘
  • HW
    • ISR 전원이 가진 위치. 컨슈머는 HW 앞까지만 읽음

동작 원리는 복제와 ISR.

acks와 min.insync.replicas

  1. 성공 응답
    • acks=1은 리더 로그에 쓰면 바로 응답
    • acks=all은 ISR 안의 복제본이 모두 받아야 응답
  2. 리더 장애
    • ISR 안의 팔로워 하나가 새 리더가 됨
  3. 결과
    • acks=1: 새 리더에 없는 4, 5는 사라짐. 프로듀서는 이미 성공으로 알고 있음
    • acks=all: 응답한 레코드는 ISR 전원에 있으므로 새 리더에도 있음
  • min.insync.replicas가 있어야 acks=all이 의미 있음
    • ISR이 리더 하나로 줄면 acks=all도 리더 혼자 받고 응답함 → acks=1과 같아짐
    • min.insync.replicas=2면 ISR이 2 미만일 때 쓰기를 거절 (NotEnoughReplicas). 유실 대신 쓰기 실패를 고르는 것
    • 복제 계수 3 + 최소 2로 브로커 하나는 죽어도 쓸 수 있게 함

unclean 리더 선출

  1. ISR이 리더 하나로 줄어듦
    • B는 3까지만 받고 뒤처져 ISR에서 빠짐
    • min.insync.replicas=1이면 A 혼자 4 ~ 6을 받고 성공 응답을 보냄
  2. A 장애
    • ISR에 남은 복제본이 없음
  3. unclean 끔 (기본값)
    • 리더를 뽑지 않고 파티션이 멈춤. 유실 대신 가용성을 포기
  4. unclean 켬
    • ISR 밖의 B가 리더가 됨 → A에만 있던 4 ~ 6 유실
    • 프로듀서는 4 ~ 6의 성공 응답을 이미 받았음
  • min.insync.replicas=2였다면 1번에서 쓰기가 거절되어 4 ~ 6이 성공으로 남지 않는다

fsync 대신 복제

  • 무슨 일이 생기나
    • 브로커는 레코드마다 디스크에 fsync하지 않음 (log.flush.interval.messages 기본값 = Long 최댓값)
    • 응답 시점에는 여러 브로커의 페이지 캐시에 있음. 복제본이 모두 동시에 전원을 잃으면 사라짐
  • 막는 법
    • 복제본을 다른 랙 · 다른 존에 둬서 동시에 죽지 않게 함

  • 2

4컨슈머

유실은 커밋 시점 · 자동 커밋 · 보존 기간에서, 중복은 재처리에서 생긴다. 재처리는 없앨 수 없으니 멱등하게 처리한다.

커밋 시점

  • 처리 전에 커밋 → 유실
    • 재시작하면 커밋한 150부터 읽음 → 처리 못 한 101 ~ 150을 건너뜀 (at-most-once)
  • 처리 후에 커밋 → 중복
    • 재시작하면 마지막 커밋 101부터 읽음 → 처리한 101 ~ 150을 또 처리 (at-least-once)
  • 막는 법
    • 처리 후에 커밋해 유실을 막고, 남는 중복은 아래 멱등 소비로 없앰

자동 커밋

  • 무슨 일이 생기나
    • enable.auto.commit=true(기본값)면 auto.commit.interval.ms(기본 5초)마다 poll() 안에서 커밋
    • 커밋하는 위치는 직전 poll()이 돌려준 레코드의 끝
    • 다른 스레드로 넘기고 바로 다음 poll()을 부르면 처리가 안 끝난 위치가 커밋됨 → 유실
  • 막는 법
    • poll 루프 안에서 다 처리하면 자동 커밋도 처리 후 커밋과 같아 안전
    • 비동기로 처리하면 자동 커밋을 끄고, 끝난 위치 중 연속된 곳까지만 직접 커밋

보존 기간과 오프셋 만료

  • 무슨 일이 생기나
    • 컨슈머가 150에 멈춘 사이 보존 기간이 지나 0 ~ 199 세그먼트가 삭제됨
    • 다시 시작하면 150은 로그 범위 밖 → auto.offset.reset을 따름
    • 기본값 latest면 400부터 읽어 150 ~ 399를 건너뜀
    • 오래 멈춰 그룹 오프셋이 만료돼도(offsets.retention.minutes 기본 7일) 같은 결과
  • 막는 법
    • lag 알림을 보존 기간보다 훨씬 짧은 기준으로 건다
    • 유실이 더 나쁘면 auto.offset.reset=earliest (대신 남은 구간을 다시 처리)

재처리가 생기는 상황

상황왜 다시 읽나줄이는 법
컨슈머 장애 · 재배포
  • 마지막 커밋 뒤부터 다시 읽음
  • 커밋 주기를 짧게
리밸런스
  • 파티션을 넘겨받은 컨슈머가 이전 주인의 마지막 커밋부터 읽음
  • 이전 주인이 처리했지만 커밋 못 한 구간이 겹침
  • 파티션을 뺏기기 직전에 커밋 (리밸런스 리스너)
처리가 max.poll.interval.ms(기본 5분) 초과
  • 그룹에서 쫓겨나 리밸런스 → 커밋 실패 → 같은 구간을 다른 컨슈머가 다시 처리
  • 값을 처리 시간보다 넉넉히
  • max.poll.records를 줄임
  • 줄일 수만 있고 없앨 수는 없다. 그래서 처리 자체를 멱등하게 만든다

멱등 소비

  • 무슨 일이 생기나
    • DB에 쓰고 오프셋 커밋 전에 죽으면 101부터 다시 읽어 또 씀
  • 막는 법
    • 두 번 처리해도 결과가 한 번만 남게 씀. 처리 성격에 따라 고름
방법하는 일맞는 경우
키로 덮어쓰기 (upsert)
  • 같은 키를 다시 쓰면 같은 결과
  • 최신 상태를 저장 (프로필 · 상품 정보)
  • 더하기 · 적립처럼 누적하는 처리에는 안 맞음
inbox
  • 처리한 event_id를 기록하고, 이미 있으면 건너뜀
  • 누적 · 상태 전이 (정산 적립, 재고 차감)
  • 메시지에 고유 id가 있어야 함
결과와 오프셋을 같이 저장
  • 처리 결과와 "읽은 위치"를 같은 DB 트랜잭션에 저장
  • 시작할 때 DB의 위치로 seek()
  • 저장소가 하나일 때
  • Kafka 그룹 커밋은 쓰지 않음
멱등 키 (외부 API)
  • API에 event_id를 멱등 키로 넘겨 같은 요청을 한 번만 반영
  • 결제 · 알림 같은 되돌릴 수 없는 호출
  • API가 지원하지 않으면 at-least-once를 받아들이고 보정

inbox

  1. poll
    • 토픽에서 이벤트를 읽음. 보내는 쪽이 넣어 둔 event_id가 함께 옴
  2. event_id 기록
    • DB 트랜잭션을 열고 inbox 테이블에 event_id를 넣음
    • 이미 있으면 들어가지 않음(0건) → 이미 처리한 이벤트
  3. 반영 또는 건너뜀
    • 1건 들어갔으면 정산에 반영, 0건이면 건너뜀
  4. COMMIT
    • inbox 기록과 정산 반영이 함께 남거나 함께 없어짐
  5. 오프셋 커밋
    • DB COMMIT 뒤에 커밋. 그 사이에 죽어 다시 읽어도 2번에서 0건 → 한 번만 반영

설정

설정기본값권장 (예시)막는 것

  • poll 루프 안 동기 처리면 true
  • 비동기 처리면 false + 직접 커밋
  • 처리 전 커밋으로 인한 유실
auto.offset.resetlatest
  • 유실이 더 나쁘면 earliest
  • 오프셋 만료 · 범위 초과 시 건너뜀

  • 처리 시간보다 넉넉히
  • 처리 지연 → 리밸런스 → 중복

5exactly-once

at-least-once 위에서 중복을 없애는 방법은 두 가지다. 멱등하게 쓰거나, 결과와 위치를 한 번에 커밋한다.

두 가지 길

at-least-once + 멱등원자적 커밋
방법
  • 두 번 와도 결과가 같게 씀
  • 결과와 읽은 위치를 함께 커밋하거나 함께 버림
예
  • 멱등 프로듀서
  • upsert · inbox · 멱등 키
  • Kafka 트랜잭션
  • Flink 2단계 커밋
  • 결과와 오프셋을 같은 DB에 저장
조건
  • 고유 id나 키가 있어야 함
  • 결과를 쓰는 곳이 트랜잭션을 지원해야 함

Kafka 트랜잭션

Kafka에서 읽어 Kafka에 쓰는 처리에서, 출력과 입력 오프셋을 한 트랜잭션으로 묶는다.

  1. begin
    • 앱이 트랜잭션을 시작 (클라이언트 안에서 상태만 바꿈)
  2. 결과 send
    • 처음 쓰는 파티션은 코디네이터에 등록한 뒤 씀
    • 결과는 출력 토픽에 실제로 들어가지만 read_committed로 읽는 쪽은 아직 못 봄
  3. 오프셋 전달
    • sendOffsetsToTransaction()으로 입력 오프셋을 같은 트랜잭션에 넣음
    • 컨슈머가 따로 커밋하지 않음
  4. commit
    • 코디네이터가 "커밋 준비"를 자기 로그(__transaction_state)에 먼저 기록
    • 이 기록이 끝나면 앱이 죽어도 커밋은 끝까지 진행됨
  5. 커밋 마커
    • 코디네이터가 등록된 모든 파티션에 커밋 마커를 씀
    • 출력 결과와 오프셋이 함께 보임. 중간에 죽으면 함께 버려짐(abort 마커)

read_committed와 LSO

  • 설정해야 동작
    • isolation.level 기본값은 read_uncommitted → 커밋 전 · abort된 레코드도 읽음
    • 트랜잭션의 효과는 읽는 쪽이 read_committed일 때만 생김
  • LSO (last stable offset)까지만 읽음
    • LSO = 아직 안 끝난 트랜잭션 중 가장 오래된 것의 시작 위치
    • 트랜잭션 하나가 오래 열려 있으면 그 뒤의 커밋된 레코드도 못 읽음 → lag이 쌓인 것처럼 보임
    • abort된 레코드는 브로커가 알려주는 목록으로 클라이언트가 걸러냄

transactional.id와 펜싱

  • 문제
    • 멈춘 줄 알았던 옛 인스턴스(좀비)가 깨어나 같은 입력의 결과를 또 씀
  • 해결
    • 같은 일을 맡은 인스턴스는 같은 transactional.id를 씀
    • 새 인스턴스가 initTransactions()를 부르면 코디네이터가 epoch를 올리고, 옛 인스턴스의 열린 트랜잭션은 abort
    • 낮은 epoch로 오는 요청은 거절 (ProducerFencedException)
  • 트랜잭션 버전 2 (KIP-890, 4.0부터)
    • 트랜잭션이 끝날 때마다 epoch를 올림
    • 앞 트랜잭션의 늦게 도착한 쓰기가 다음 트랜잭션에 섞이는 것(hanging transaction)을 브로커가 거절

Kafka Streams

  • processing.guarantee=exactly_once_v2
    • 위 트랜잭션 과정을 프레임워크가 대신 함. 상태 저장소의 changelog 쓰기도 같은 트랜잭션에 들어감
    • 기본값은 at_least_once
    • 켜면 commit.interval.ms 기본값이 30초 → 100ms로 바뀜 (결과가 빨리 보이게)

Flink 2단계 커밋

  • 체크포인트에 맞춘 트랜잭션
    • 체크포인트로 복구하면 바깥에 이미 쓴 결과가 남음 → 싱크가 트랜잭션으로 쓰고 체크포인트 완료 때 커밋
    • 자세한 흐름은 싱크의 exactly-once
    • Kafka 싱크라면 transaction.timeout.ms를 체크포인트 간격 + 복구 시간보다 길게, 브로커 최대값 이하로

경로별로 고르기

경로방법
Kafka → Kafka
  • Kafka 트랜잭션 또는 Kafka Streams exactly_once_v2
  • 읽는 쪽 read_committed
DB → Kafka
  • outbox + 멱등 프로듀서
  • 남는 재발행 중복은 받는 쪽 inbox
Kafka → DB
  • inbox 또는 결과와 오프셋을 같은 DB에 저장
Kafka → 외부 API
  • 멱등 키
  • 없으면 at-least-once + 보정
Kafka → Flink → 바깥
  • Flink 2단계 커밋 싱크
  • 지원하지 않는 싱크는 멱등 쓰기

설정

설정기본값설명
isolation.level (컨슈머)read_uncommitted
  • 트랜잭션 토픽을 읽으면 read_committed
transaction.timeout.ms (프로듀서)60초
  • 이 시간 안에 커밋 안 하면 코디네이터가 abort
  • 커밋 주기보다 길게
transaction.max.timeout.ms (브로커)15분
  • 프로듀서가 요청할 수 있는 최대값. 넘으면 초기화 실패
transactional.id.expiration.ms (브로커)7일
  • 이 기간 동안 안 쓰인 transactional.id 상태를 지움
  • 이 문서의 기본값은 Kafka 4.4.0 소스 태그의 설정 정의 기준
