Flink 조인과 상태

스트림끼리 조인하면 왜 상태가 커지고, 조인 종류마다 무엇을 얼마나 들고 있는지 본다. 옵션은 Flink 2.2 기준.

1조인이 상태를 쌓는 이유

  1. 들어오면 저장
    • keyBy로 같은 키는 같은 서브태스크에 모임
    • 레코드는 자기 쪽 대기 상태에 키별로 저장
  2. 짝을 찾으면 결과
    • 반대쪽 대기 상태에서 같은 키를 찾아 결과를 냄
    • 찾아도 지우지 않음 — 같은 키의 다음 레코드도 짝이 될 수 있음
  3. 계속 쌓임
    • 짝이 언제 올지 모르니 시간 제한이 없으면 양쪽을 영원히 보관
    • 상태가 끝없이 커짐 → 메모리 · 체크포인트 크기 · 복구 시간이 함께 늘어남
  • 셔플(keyBy)은 같은 키를 모으려고 일어날 뿐, 상태가 커지는 원인은 "보관 기간이 없음"

2조인 종류와 병목

종류를 가르는 기준은 "상태를 얼마나 들고 있나"다.

일반 조인

A JOIN B ON A.id = B.id
  • 상태
    • 양쪽 전부, 지우지 않음
    • TTL을 걸면 그만큼 지나 지움
    • TTL 뒤에 온 짝은 못 만남
  • 결과
    • inner: 추가만
    • outer: 짝이 늦게 오면 앞서 낸 결과를 고침
  • 사례
    • 주문 × 결제
    • 언제 짝이 올지 모름
  • 병목
    • 인기 상품 키에 레코드가 몰려 한 서브태스크만 바쁨 (핫 키)
    • 그 서브태스크의 상태만 끝없이 커져 체크포인트 · 복구가 느려짐
    • 같은 키에 쌓인 레코드가 많으면 짝 하나에 결과 N개가 쏟아짐
    • outer 조인은 늦은 짝마다 앞선 결과를 고쳐 하류 부하가 큼
  • 대응
    • TTL로 보관 기간 제한
    • 핫 키는 키에 접미사를 붙여 나눈 뒤 다시 합침
    • 가능하면 구간 조인으로 바꿈

구간 조인 (interval)

… AND A.ts BETWEEN B.ts - INTERVAL '30' MINUTE AND B.ts
  • 상태
    • 시간 구간 안의 양쪽 레코드
    • 워터마크가 구간을 지나면 지움
  • 결과
    • 추가만
  • 사례
    • 광고 노출 × 클릭
    • 노출 후 30분 안의 클릭만
  • 병목
    • 워터마크가 멈추면(쉬는 파티션) 지울 시점이 안 와 상태가 계속 쌓임
    • 구간을 넓게 잡으면 그만큼 상태가 큼
    • 두 스트림의 지연 차가 크면 빠른 쪽을 오래 들고 있음
  • 대응
    • 쉬는 파티션 제외 (워터마크)
    • 구간을 실제 필요만큼만

윈도우 조인

같은 윈도우 TVF(TUMBLE 등)를 씌운 두 테이블을 window_start · window_end로 조인
  • 상태
    • 지금 윈도우의 양쪽 레코드
    • 윈도우가 닫히면 지움
  • 결과
    • 추가만
  • 사례
    • 1분 단위 주문 수 × 1분 단위 방문 수
  • 병목
    • 윈도우가 닫힐 때 결과가 한꺼번에 나와 순간 부하
    • 워터마크보다 늦은 데이터는 버려짐
  • 대응
    • 윈도우 크기 · 허용 지연 조정

temporal 조인 (이벤트 시간)

A JOIN B FOR SYSTEM_TIME AS OF A.ts ON …
  • 상태
    • 차원 쪽의 키별 버전
    • 워터마크가 지나 더 안 쓰일 옛 버전은 지움
    • B는 기본 키 + 이벤트 시간이 있는 버전 테이블, 양쪽 모두 워터마크 필요
  • 결과
    • 추가만
    • 차원이 나중에 바뀌어도 앞서 낸 결과는 안 고침
  • 사례
    • 주문 × 환율 (주문 시점의 환율)
    • 이벤트 × 상품 가격 CDC
  • 병목
    • 차원 쪽 변경이 드물면 그쪽 워터마크가 안 올라감
    • 결과는 낮은 쪽 워터마크까지만 나와 주문이 "결과 대기"에 묶임
    • 차원 키가 많으면 버전 상태가 큼
  • 대응
    • 차원 쪽 쉬는 소스 제외 (table.exec.source.idle-timeout)

lookup 조인

A JOIN B FOR SYSTEM_TIME AS OF A.proc_time ON …
  • 상태
    • 없음 (캐시는 선택)
    • B는 조회를 지원하는 소스 (JDBC · Paimon 등)
  • 결과
    • 추가만
    • 조회한 순간의 값을 붙임
  • 사례
    • 클릭 로그 × 상품 메타 DB
  • 병목
    • 레코드마다 외부 조회 → 조회 지연이 곧 처리 지연
    • 버퍼가 차서 백프레셔가 소스까지 번짐
    • 외부 DB에 조회 부하가 몰림
    • 메타가 로그보다 늦게 생기면 못 붙음
  • 대응
    • 비동기 조회 · 캐시 (캐시는 최신성과 교환)
    • LOOKUP 힌트로 못 찾으면 재시도

3고르는 기준

상황조인
  • 양쪽 다 이벤트 스트림
  • 짝이 일정 시간 안에 옴 (클릭 후 30분 안의 주문)
구간 조인
  • 같은 시간 단위로 묶어 맞춤
윈도우 조인
  • 이벤트에 "그 시점의" 차원 값을 붙여야 함
  • 차원도 변경 스트림 (CDC)
temporal 조인
  • 차원이 DB · 테이블에 있음
  • 조회 순간의 최신 값이면 충분
lookup 조인
  • 짝이 언제 올지 모르고 시간 제한도 못 정함
일반 조인 + TTL

TTL과 lookup의 한계

  • TTL
    • TTL이 지난 뒤 온 짝은 조인되지 않아 결과가 빠짐
  • lookup
    • 차원이 이벤트보다 늦게 들어오면 못 붙음 → LOOKUP 힌트의 재시도로 보완
    • 매 레코드 외부 조회라 느림 → 비동기 조회와 캐시로 보완
  • temporal
    • 워터마크를 기다려 결과를 내므로 지연이 생김

4상태 백엔드와의 관계

  • 조인의 대기 데이터 = 키별 상태
    • 조인이 상태를 쌓는 이유의 "클릭 대기 · 주문 대기"가 상태 백엔드에 키별로 저장됨
    • 서브태스크마다 자기 키 그룹의 대기 데이터만 가짐
  • 상태가 크면 RocksDB
    • 일반 조인 · 넓은 구간 조인은 GB 단위로 커지기 쉬움
    • 힙에 안 들어가면 RocksDB, 증분 체크포인트를 같이 켬
  • TTL이 디스크를 줄이는 때
    • RocksDB에서는 만료된 값이 컴팩션 때 실제로 지워짐
  • 상태 크기가 곧 체크포인트 크기
    • 조인 상태가 크면 체크포인트 업로드 · 복구 다운로드가 함께 느려짐

5설정 한눈에

설정기본값설명
table.exec.state.ttl0 ms (안 지움)
  • 잡 전체 상태 TTL
  • 일정 시간 갱신 안 된 상태를 지움
/*+ STATE_TTL('A'='1d', 'B'='12h') */—
  • 일반 조인 · 집계에 연산자 단위 TTL
  • 위 잡 전체 값보다 우선
/*+ LOOKUP('table'='B', 'async'='true', …) */—
  • lookup 조인의 비동기 · 재시도
  • 재시도: 'retry-predicate'='lookup_miss', 'retry-strategy'='fixed_delay', 'fixed-delay', 'max-attempts'를 함께 지정
lookup.cacheNONE
  • PARTIAL로 켜면 조회 결과를 캐시
  • 커넥터 옵션 (JDBC 기준)
lookup.partial-cache.max-rows
lookup.partial-cache.expire-after-write		없음
  • 캐시 크기 · 유효 시간

6한 장 요약

  • 원인
    • 조인은 짝을 기다리느라 양쪽을 상태에 보관
    • 보관 기간이 없으면 상태가 끝없이 커짐
  • 종류
    • 일반 — 전부 영원히, TTL로 제한
    • 구간 · 윈도우 — 시간 범위만, 워터마크로 지움
    • temporal — 차원의 버전만
    • lookup — 상태 없이 외부 조회
  • 병목
    • 일반 · 구간 · temporal — 상태가 커지거나 워터마크가 멈춰 안 지워짐
    • lookup — 외부 조회 지연이 백프레셔로 번짐
    • 공통 — 핫 키가 한 서브태스크에 몰림
  • 상태 백엔드
    • 조인 대기 데이터가 곧 키별 상태 → 크면 RocksDB + 증분 체크포인트
  • 고르기
    • 짝이 오는 시간을 알면 구간 조인, 차원이면 temporal · lookup
    • TTL은 늦게 온 짝을 놓치는 대가가 있음
