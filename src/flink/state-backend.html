상태 백엔드란

  • 상태
    • 연산자가 다음 레코드를 처리하려고 들고 있는 값
    • 형태는 값 하나(ValueState), 목록(ListState), 맵(MapState) 등
  • 상태 백엔드
    • 그 상태를 어디에 두고 어떻게 읽고 쓸지 맡는 저장소
    • TaskManager 안에, 서브태스크마다 자기 영역이 따로 있다
      • keyBy로 같은 키는 항상 같은 서브태스크로 간다
      • 각 서브태스크는 자기 키 그룹의 상태만 가진다 (서브태스크마다 따로)
    • 사용자 코드는 value()로 꺼내고 update()로 넣기만 한다
    • 꺼낼 때 키를 넘기지 않는다 — Flink가 레코드의 키(상품 A)를 현재 키로 먼저 정해 두고, 백엔드는 그 키의 칸을 돌려준다
    • 그래서 count는 변수 하나처럼 보여도, 현재 키에 따라 다른 칸을 가리키는 키별 저장소의 창구다

종류: HashMap과 RocksDB

대표적인 상태 백엔드는 두 가지 — 처리 중 상태를 JVM 힙에 두는 HashMap, 로컬 디스크에 두는 RocksDB.

HashMapRocksDB
상태 위치
  • JVM 힙
  • 자바 객체 그대로
  • TM 로컬 디스크 + 네이티브 메모리
  • 바이트로 직렬화
읽기 · 쓰기
  • 해시맵 조회 한 번 → 빠름
  • 매번 직렬화 · 역직렬화
  • 메모리에 없으면 디스크
크기 한계
  • 힙
  • 디스크
메모리 위험
  • 힙 OOM
  • GC 지연
  • 네이티브 메모리 초과 → 컨테이너 OOMKilled
체크포인트
  • 매번 전체
  • 증분 가능 (새 파일만)
관리 메모리
  • 안 씀
  • 씀 (memtable · 블록 캐시)

백엔드 선택 기준

상황고를 것같이 챙길 것
  • 상태가 힙에 넉넉히 들어감
  • 지연이 중요
HashMap
  • 관리 메모리를 안 쓰니 taskmanager.memory.managed.fraction을 낮춰 힙으로 돌림
  • 상태가 GB 단위
  • 긴 윈도우 · 조인 · 대기 버퍼처럼 계속 쌓임
RocksDB
  • 증분 체크포인트 켜기
  • 상태 TTL로 크기 관리
RocksDB로 바꿀 때 주의 — 받은 값은 사본
  • value()로 받은 객체를 고치고 update()를 안 부르면 저장되지 않는다
  • HashMap에서는 같은 객체라 우연히 동작하던 코드가, RocksDB로 바꾸면 깨지는 흔한 이유

서브태스크마다 따로인 상태 백엔드

항목내용
있는 곳
  • TM 프로세스 안
  • 상태가 있는 서브태스크마다 하나씩 따로 뜸
담는 것
  • 자기 서브태스크가 맡은 키 그룹의 상태만
  • 다른 서브태스크와 공유하지 않음
공유가 필요 없는 이유
  • keyBy로 같은 키는 항상 같은 서브태스크로 옴
  • 락이 필요 없고, 병렬도를 늘리면 그대로 확장됨
  • 체크포인트도 서브태스크마다 자기 상태만 올리면 됨
같이 쓰는 것
  • JVM 힙 · 관리 메모리 · 로컬 디스크 같은 자원만
모두가 같은 데이터를 봐야 하면
  • broadcast 상태
  • 이것도 공유가 아니라 서브태스크마다 같은 사본을 둠

RocksDB 쓰기: LSM 트리

  1. update()는 메모리의 memtable에만 넣고 끝난다.
    • 디스크를 건드리지 않아 빠르다
  2. memtable이 정해진 크기에 차면 읽기 전용으로 돌리고, 새 memtable로 쓰기를 계속 받는다.
  3. 읽기 전용 memtable을 정렬된 그대로 디스크에 SST 파일로 내려쓴다(flush).
    • 이 파일들이 L0다
    • SST는 한 번 쓰면 고치지 않는다
  4. 파일이 쌓이면 백그라운드 컴팩션이 파일을 합치며 아래 레벨(L1, L2 …)로 내린다.
    • 같은 키의 옛 값과 지운 값은 이때 버려진다

불변 파일과 레벨

항목내용
같은 키를 다시 쓰면
  • 옛 값은 그대로 두고, 새 파일에 새 값을 쓴다
  • 위쪽(최근) 파일의 값이 진짜
레벨별 키 범위
  • L0 — 파일끼리 키 범위가 겹친다
  • L1부터 — 같은 레벨 안에서는 겹치지 않는다 (그림의 a ~ h, i ~ p …)
장애 대비 로그 (WAL)
  • Flink는 RocksDB의 WAL을 끈다
  • 내구성은 체크포인트가 맡는다

읽기 경로와 캐싱

  1. memtable → 읽기 전용 memtable 순으로 본다.
  2. L0는 전부 최신 파일부터 본다.
    • 키 범위가 겹쳐서 어느 파일에 있을지 모르기 때문이다
  3. L1부터는 레벨당 한 파일만 본다.
    • 파일별 키 범위 목록으로 키가 들어갈 파일을 바로 고른다
    • 찾으면 거기서 멈춘다
  4. 파일 하나는 블룸 필터 → 인덱스 블록 → 데이터 블록 순으로 좁힌다.
    • 블룸 필터가 "확실히 없음"이면 파일을 열지 않는다
    • 인덱스로 데이터 블록 하나를 고른다
    • 데이터 블록은 블록 캐시(메모리)에 있으면 디스크까지 가지 않는다

tombstone과 읽기 증폭

항목내용
처음 찾은 값이 정답
  • 위가 최신
  • 아래 레벨에 같은 키의 옛 값이 있어도 보지 않음
삭제 (tombstone)
  • 지우면 "지워짐" 표시를 새로 씀
  • 위에서 이 표시를 먼저 만나면 "없음"
읽기 증폭
  • 키 하나를 읽으려고 여러 곳을 보는 것
  • 찾는 키가 없을 때 가장 비쌈 (끝까지 내려가야 함)
  • 블룸 필터와 컴팩션이 줄여 줌

write stall과 TTL 정리

항목내용
실행
  • 백그라운드 스레드
  • TM의 CPU · 디스크를 씀
못 따라가면 (write stall)
  • L0가 계속 쌓이면 RocksDB가 쓰기를 늦추거나 멈춤
  • 그 연산자가 느려져 백프레셔로 번짐
상태 TTL 정리
  • 만료된 값도 컴팩션 때 실제로 지워짐 (컴팩션 필터)
  • TTL을 걸어도 디스크 공간은 컴팩션이 돌아야 줄어듦
위 기준값
  • RocksDB 기본값
  • Flink 사전 설정 옵션에 따라 다를 수 있어 실제 잡 설정으로 확인

메모리

항목내용
어디에 잡히나
  • memtable · 블록 캐시는 JVM 힙 밖의 네이티브 메모리
크기를 정하는 것
  • 관리 메모리에서 몫을 정해 줌
  • state.backend.rocksdb.memory.managed (기본 켜짐)
  • 같은 슬롯의 RocksDB들이 이 몫을 나눠 씀
계산 밖 네이티브 메모리
  • 예: 싱크의 파일 쓰기 버퍼, 외부 라이브러리의 lookup 캐시
  • taskmanager.memory.jvm-overhead.fraction (기본 0.1, 최소 192MB · 최대 1GB)로 여유를 둠
한도를 넘으면
  • JVM OOM이 아니라 쿠버네티스가 파드를 죽임 (OOMKilled)
  • 힙 덤프로는 원인이 안 보임

체크포인트와의 연결

백엔드와 S3의 관계

HashMapRocksDB
설정
  • state.backend.type: hashmap (기본)
  • state.backend.type: rocksdb
  • execution.checkpointing.incremental: true (기본 꺼짐)
올릴 곳 (공통)
  • execution.checkpointing.dir: s3://… (옛 이름 state.checkpoints.dir)
  • 안 주면 JM 메모리에 둠 — JM이 죽으면 사라짐
③ 사본 올리기
  • 힙의 상태를 직렬화해 매번 전체 올림
  • memtable을 SST로 내려쓴 뒤 새로 생긴 SST만 올림
④ 복원
  • S3의 사본을 힙으로 읽어 들임
  • 필요한 SST를 로컬 폴더로 내려받음
  • 그 파일들로 RocksDB를 다시 엶

RocksDB 증분 체크포인트

  1. 체크포인트 N
    • memtable을 먼저 SST로 내려씀
    • 살아 있는 SST 1 · 2 · 3을 S3에 올림
  2. 컴팩션
    • 그 사이 SST 1 · 2를 합쳐 새 파일 4 · 5를 만듦
  3. 체크포인트 N+1
    • 새로 생긴 4 · 5만 올림
    • 3은 이미 S3에 있으니 참조만 함
    • 가능한 이유: SST는 한 번 쓰면 바뀌지 않음
  4. 정리
    • 체크포인트 N이 만료되면 아무도 참조하지 않는 1 · 2를 지움
  • 주의
    • 컴팩션 직후에는 새 파일이 많아 다음 체크포인트 크기가 튈 수 있음

체크포인트 자체의 흐름(배리어, 목차, 복구)은 체크포인트와 장애 복구.

한 장 요약

  1. 상태는 연산자가 레코드 사이에 들고 있는 값이고, 코드는 현재 키에 맞춰진 창구로 읽고 쓴다.
  2. 상태 백엔드는 상태가 있는 서브태스크마다 따로 있고, 자기 키 그룹만 갖는다.
  3. HashMap은 힙에 객체로 둬서 빠르고, RocksDB는 디스크에 바이트로 둬서 크게 담는다.
  4. RocksDB는 LSM이라 쓰기는 memtable에 넣고 끝나며, 파일은 불변이고 컴팩션으로 정리된다.
  5. 읽기는 위 레벨부터 찾고, 블룸 필터와 블록 캐시가 디스크 접근을 줄인다.
  6. 파일이 불변이라 체크포인트 때 새 파일만 올리는 증분 체크포인트가 가능하다.
