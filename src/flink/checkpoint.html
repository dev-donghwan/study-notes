  • 체크포인트는 모든 서브태스크의 상태와 소스의 읽은 위치를 같은 경계로 저장하는 장치다.

배리어로 찍는 과정

  • 배리어
    • 소스가 데이터 줄 사이에 끼워 넣는 표시
    • 레코드와 같은 줄에 서서 흐르고, 레코드를 앞지르지 않는다
    • 배리어 N보다 앞(오른쪽)의 레코드는 체크포인트 N에 반영되고, 뒤(왼쪽)는 다음 체크포인트 몫이다
    • 그림은 배리어 N이 연산자를 막 지나간 순간 — 소스와 연산자는 저장을 마쳤고, 싱크는 배리어가 오기를 기다린다
    • 그래서 각 서브태스크가 "배리어를 만난 순간"의 상태를 저장하면, 모두가 같은 경계로 저장된다

역할별 배리어 처리

  1. 소스
    • JobManager가 체크포인트 N 시작을 알림
    • 읽은 위치(5)를 저장
    • 데이터 사이에 배리어 N을 끼워 보내고, 멈추지 않고 계속 읽음
  2. 연산자
    • 배리어 앞의 r5까지 처리해 합계 5
    • 배리어를 만난 순간 합계 5를 저장하고 배리어를 넘김
    • 처리 위치는 따로 보내지 않음 — 배리어 앞까지만 반영된 상태라 소스의 위치 5와 저절로 짝이 맞음
  3. 싱크
    • 써 두었지만 아직 확정하지 않은 결과 목록을 저장
  4. 완료
    • 보고가 다 모이면 JobManager가 목차(_metadata)를 쓰고 완료 처리
    • 완료 알림을 받은 싱크가 결과를 커밋 → 외부에 보임
    • 타임아웃 안에 다 안 모이면 N은 버리고 이전 완료본을 그대로 씀

동기 사본과 비동기 업로드

  1. 사본 확보 (동기)
    • 배리어를 만난 순간, 그 시점 상태의 사본만 빠르게 떠 둔다
    • 이 짧은 순간만 레코드 처리가 멈춘다
  2. 업로드 (비동기)
    • 떠 둔 사본을 각 서브태스크가 S3에 직접 올린다
    • 그동안 레코드 처리는 계속된다
  3. 보고
    • 업로드가 끝나면 JobManager에 "완료 + 파일 위치"만 보낸다
    • 상태 자체는 JobManager를 거치지 않는다 — 상태가 수십 GB여도 JobManager가 병목이 되지 않는다

장애와 복구

TaskManager 장애

  1. heartbeat가 끊기거나 쿠버네티스가 파드 종료를 알린다.
  2. JobMaster가 재시작 전략에 따라 관련 서브태스크(보통 잡 전체)를 취소한다.
  3. ResourceManager가 쿠버네티스에 새 TM 파드를 요청한다.
  4. 마지막 완료 체크포인트의 목차를 읽어, 각 서브태스크가 S3에서 자기 상태를 받아 복원한다.
  5. 소스는 체크포인트에 저장된 위치부터 다시 읽는다.
    • 상태와 읽은 위치가 같은 체크포인트로 함께 되돌아가므로, 다시 읽은 레코드가 두 번 반영되지 않는다 — Flink 내부의 exactly-once
    • 끝단까지 보장하려면 소스는 다시 읽을 수 있어야 하고(예: Kafka), 싱크는 체크포인트 완료 때 커밋해야 한다(2단계 커밋)

JobManager 장애

  1. 쿠버네티스(Deployment)가 새 JM 파드를 띄운다.
  2. 새 JM이 HA ConfigMap에서 리더 정보와 최신 체크포인트 위치를, HA 저장소(S3)에서 잡 정보를 읽는다.
  3. 잡을 재구성하고, TM들이 새 JM에 다시 붙어 마지막 체크포인트에서 상태를 복원한다.
  4. HA가 꺼져 있으면
    • 2번에서 읽을 정보가 없어, 잡이 상태 없이 처음부터 시작한다

한 장 요약

  1. 체크포인트는 모든 서브태스크의 상태와 소스의 읽은 위치를 같은 경계로 저장한다.
  2. 경계는 소스가 데이터 사이에 끼워 보내는 배리어가 만든다.
    • 각 서브태스크는 배리어를 만난 순간의 상태를 S3에 올린다
  3. 입력이 둘이면 배리어를 맞춰 기다리고, 백프레셔나 큰 상태가 체크포인트를 느리게 한다.
  4. 장애가 나면 상태와 위치를 함께 마지막 체크포인트로 되돌려 다시 읽는다.
    • 계획된 재배포는 세이브포인트나 마지막 체크포인트로 시작한다
