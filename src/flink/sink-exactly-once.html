문제: 바깥에 쓴 결과의 중복

  1. 체크포인트 N
    • 읽은 위치 100과 합계 100을 저장
    • 싱크 토픽에는 100까지의 결과가 있음
  2. 101 ~ 150 처리
    • 위치 150 · 합계 150
    • 결과를 싱크 토픽에 바로 씀 → 읽는 쪽이 곧바로 봄
  3. 장애 → N으로 복구
    • Flink 칸은 위치 100 · 합계 100으로 되돌아감
    • 싱크 토픽에 이미 쓴 101 ~ 150은 되돌아가지 않음
  4. 101 ~ 150 다시 처리
    • 같은 결과를 또 씀 → 싱크 토픽에 두 번 남음 (at-least-once)

2단계 커밋 정상 흐름

싱크가 결과를 트랜잭션 안에 쓰고, 체크포인트가 완료될 때만 커밋한다.

  1. 체크포인트 N
    • 그림 1과 같음
  2. 트랜잭션 T1 열기
    • 싱크가 싱크 토픽에 트랜잭션 T1을 엶
  3. T1에 씀
    • 101 ~ 150의 결과를 T1 안에 기록
    • 데이터는 싱크 토픽에 실제로 들어가지만 커밋 전이라 read_committed로 읽는 쪽은 못 봄
  4. 배리어 N+1 · 사전 커밋 (1단계)
    • 배리어가 싱크에 오면 T1을 마감 (flush, 더는 안 씀)
    • 체크포인트 N+1에 세 가지를 같이 저장
      • 소스: 읽은 위치 150
      • 연산자: 합계 150
      • 싱크: 아직 커밋 안 한 트랜잭션 이름 T1
    • 이후 결과는 새로 연 T2에 씀
    • T1 이름을 저장하는 이유
      • N+1 완료 직후, T1 커밋 전에 죽으면 N+1로 복구해 위치 150부터 읽음
      • 101 ~ 150은 다시 처리하지 않으므로 T1 이름이 없으면 결과가 사라짐
      • 이름이 있으면 복구하면서 T1을 마저 커밋
  5. N+1 완료 → T1 커밋 (2단계)
    • JobManager가 모든 서브태스크의 저장 완료를 확인하고 완료를 알림
    • 싱크가 T1을 커밋 → T1의 데이터가 한 번에 보임

단계를 둘로 나누는 이유

  • 체크포인트는 전원이 성공해야 유효
    • 소스 · 연산자 · 싱크 중 하나라도 저장에 실패하면 N+1은 무효
  • 무효인 체크포인트의 결과가 보이면 안 됨
    • 그래서 1단계에서 "언제든 커밋할 수 있게" 준비만 하고
    • JobManager가 전원 성공을 확인한 뒤에 2단계로 커밋

커밋 전에 죽으면

  1. 체크포인트 N
    • 그림 1과 같음
  2. T1을 열고 쓰다가 장애
    • 체크포인트 N+1이 완료되기 전에 죽음
    • T1은 커밋 전이라 아직 아무도 못 봄
  3. N으로 복구 · T1 롤백
    • Flink 칸은 위치 100 · 합계 100으로 되돌아감
    • T1은 커밋된 적 없어 롤백(abort) → 싱크 토픽에 남아 있어도 끝까지 안 보임
    • 바깥 결과도 Flink와 함께 되돌아간 셈
  4. T1' 열고 다시 씀
    • 새 트랜잭션 T1'을 열고 101 ~ 150을 다시 기록
    • 아직 커밋 전이라 안 보임
  5. N+1 완료 → T1' 커밋
    • T1'만 커밋 → 읽는 쪽은 101 ~ 150을 한 번만 봄

죽은 시점별로 보면

죽은 시점복구할 때결과
N+1 완료 전
  • N으로 복구, N에 저장된 표에는 T1이 없음
  • T1은 버리고 다시 씀
한 번
N+1 완료 후, T1 커밋 전
  • N+1로 복구, 표에 T1이 있음
  • T1을 마저 커밋
한 번
T1 커밋 후
  • N+1로 복구, T1을 다시 커밋해도 이미 커밋된 상태
한 번
  • 두 번째 · 세 번째 줄 때문에 커밋은 여러 번 해도 결과가 같아야 한다

대상마다 다른 구현

정하는 쪽정하는 것
Flink
  • 언제 — 쓰기 · 사전 커밋 · 커밋, 세 시점은 모든 싱크가 같음
싱크 (커넥터)
  • 무엇을 — 각 시점에 할 일을 대상 시스템의 기능으로 구현

대상별로 세 시점에 하는 일

대상쓰는 동안 (안 보임)사전 커밋 (배리어)커밋 (체크포인트 완료)
Kafka
  • 트랜잭션 안에 씀
  • flush
  • 트랜잭션 id 저장
  • 트랜잭션 커밋
파일 (HDFS)
  • 숨김 이름의 작성 중 파일에 씀
  • 파일을 닫음
  • 파일 경로 저장
  • 정식 이름으로 변경
파일 (S3)
  • 멀티파트 업로드로 조각을 올림
  • 마지막 조각 올림
  • 업로드 id 저장
  • 업로드 완료 요청
Paimon · Iceberg
  • 테이블 폴더에 데이터 파일을 씀
  • 읽는 쪽은 스냅샷에 적힌 파일만 읽어서 안 보임
  • 새 파일 목록 저장
  • 그 파일들을 담은 새 스냅샷 커밋
  • 커미터 하나가 전 서브태스크 목록을 모아 한 번에
관계형 DB (XA)
  • XA 트랜잭션 안에 씀
  • XA PREPARE
  • 트랜잭션 id 저장
  • XA COMMIT
  • 저장 = 체크포인트에 같이 저장
  • 복구 후 이 id · 경로로 마저 커밋
  • Kafka는 읽는 쪽이 read_committed여야 커밋 전 데이터가 안 보임

2단계 커밋이 되려면

대상이 갖춰야 할 것예
써 두되 안 보이게, 나중에 한 번에 보이게
  • 트랜잭션 · 이름 변경 · 업로드 완료 · 스냅샷 커밋
다른 프로세스가 id만으로 이어서 커밋
  • 트랜잭션 id · 파일 경로 · 업로드 id
  • 못 갖춘 대상 (ES · Redis 등)
    • 키로 덮어쓰는 멱등 쓰기로 같은 결과를 냄 (ES 문서 _id, DB upsert)
    • 그것도 안 되면 at-least-once를 받아들임

한 장 요약

  • 문제
    • 체크포인트는 Flink 안(위치 · 상태)만 되돌림
    • 바깥에 이미 쓴 결과는 못 되돌려 재처리 구간이 중복됨
  • 해결
    • 싱크가 트랜잭션 안에 써서 커밋 전에는 안 보이게 둠
    • 커밋 시점을 체크포인트 완료에 맞춤
  • 2단계 커밋
    • 사전 커밋 (배리어) — 트랜잭션 마감 · flush, 트랜잭션 id를 체크포인트에 저장
    • 커밋 (체크포인트 완료) — JobManager가 전원 성공을 확인한 뒤 커밋
  • 장애
    • 완료 전에 죽으면 롤백하고 다시 씀
    • 완료 후 커밋 전에 죽으면 저장된 id로 마저 커밋
    • 어느 경우든 읽는 쪽에는 한 번만 보임
  • 대상
    • Kafka 트랜잭션 · 파일 이름 변경 · 스냅샷 커밋 · XA로 구현
    • 안 되는 대상은 멱등 쓰기로 대신함
