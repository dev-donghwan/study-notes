제출

  1. FlinkDeployment 적용
    • 사용자가 잡 정의를 쿠버네티스에 적용
    • 담는 것: 잡 jar · 병렬도 · 자원 · 설정
  2. JM 리소스 생성
    • Operator가 쿠버네티스에 아래 리소스를 만듦
    리소스용도
    Deployment → JM 파드
    • JobManager 프로세스 실행
    Service <이름>-rest
    • 웹 UI · REST API (8081)
    • 사용자 접속
    • Operator가 잡 상태 조회 · 세이브포인트 지시
    Service <이름>
    • JM 내부 통신 (RPC 6123, blob 6124)
    • 파드 IP가 바뀌어도 TM이 JM을 찾는 고정 주소
    ConfigMap
    • flink-conf와 로그 설정
    • JM · TM이 같은 설정으로 뜨게 함
  3. JM 시작
    • JM 파드가 뜨면 잡을 받아 실행 준비를 함 (JM 파드가 뜨면서 하는 일)
  4. HA 기록 (HA를 켠 경우)
    • Operator가 아니라 JM이 HA용 ConfigMap을 직접 만듦
    • ConfigMap에는 위치만 기록
      • 지금 리더인 JM
      • 잡 그래프 · 완료된 체크포인트가 있는 위치
    • 실제 데이터는 S3 같은 저장소에 둠 (high-availability.storageDir)
    • JM이 죽으면 새 JM이 이 ConfigMap을 읽고 이어 감 (장애와 복구)
  • TM은 Operator가 만드는 게 아니라 JM 안에서 ResourceManager가 직접 생성한다

JM 파드가 뜨면서 하는 일

  1. JM 파드 시작
    • Dispatcher와 ResourceManager가 뜬다
    • 이 시점에 TM은 0개다
  2. Dispatcher가 사용자 main()을 실행해 잡 그래프를 얻는다.
  3. Dispatcher가 이 잡을 맡을 JobMaster를 만들고 잡 그래프를 넘긴다.
  4. JobMaster가 잡 그래프를 병렬도만큼 펼쳐 "슬롯 4개 필요"를 계산하고, ResourceManager에 슬롯을 요청한다.
  5. ResourceManager는 빈 슬롯이 없으니 쿠버네티스에 TM 파드 2개를 요청한다.
  6. TM이 떠서 ResourceManager에 등록하고, 자기 슬롯 수를 보고한다.
  7. ResourceManager가 이 슬롯을 요청한 JobMaster를 알려 주면, TM이 JobMaster에 슬롯을 직접 제공한다.
  8. JobMaster가 받은 슬롯에 서브태스크를 배포하고, TM이 스레드로 실행한다.
구성 요소한 줄 역할하는 일
Dispatcher접수 창구
  • 잡 접수 (application 모드에서는 main() 실행)
  • 잡을 맡을 JobMaster 생성 (session 모드는 잡마다 하나씩)
  • 웹 UI · REST 제공
  • 끝난 잡 기록 보관
JobMaster잡 하나의 감독
  • 실행 그래프 생성
  • 슬롯 요청 · 수령
  • 서브태스크 배포와 상태 추적
  • 실패 시 재시작
  • 체크포인트 지휘
  • 잡(잡 그래프) 하나당 하나 — 서브태스크마다가 아님
ResourceManager자원 장부 관리자
  • TM 등록 · heartbeat
  • 빈 슬롯 장부 관리
  • 슬롯 요청에 빈 슬롯 배정
  • 모자라면 TM 파드 요청
  • 오래 노는 TM 반납

코드가 잡 그래프가 되기까지

  1. 사용자 코드
    • DataStream · SQL 코드는 연산자들의 연결
    • 소스, 변환, 집계, 싱크가 각각 연산자
  2. 잡 그래프 만들기
    • application 모드에서는 JM 안에서 Dispatcher가 사용자 main()을 실행해 잡 그래프(JobGraph)를 만듦
  3. 체이닝 결정
    • 묶임 — 바로 이어지고(forward) 병렬도가 같은 연산자는 한 태스크로, 한 스레드에서 돎
    • forward — 0번 → 0번, 1번 → 1번으로 그대로 이어져 묶을 수 있음 (오른쪽 그림)
    • keyBy — 키마다 갈 서브태스크가 달라 엇갈려 보내야 하므로 끊김
    • 그 밖에 끊기는 경우
      • rebalance · broadcast 같은 재분배
      • 병렬도가 다름
      • 입력이 둘인 연산자 (조인 등)
      • 직접 끊음 (disableChaining() 등)
  4. 결과
    • 태스크 2개
    • 실행할 때는 태스크마다 병렬도만큼 복제됨 (실행 계획)
    • 잡 그래프는 JobMaster에 넘어감
체이닝장점단점
묶음
  • 직렬화 · 버퍼 없이 함수 호출로 전달
  • 지연 작음
  • 한 스레드라 코어 하나를 나눠 씀
  • 누가 느린지 지표로 안 보임
끊음
  • 연산자별 병렬도
  • 연산자별 지표
  • 직렬화 · 버퍼 비용

체이닝 직접 조절하기

방법범위효과
pipeline.operator-chaining.enabled: false잡 전체체이닝을 끔
.disableChaining()연산자 하나앞뒤와 모두 끊음
.startNewChain()연산자 하나여기서부터 새 체인
.slotSharingGroup("이름")연산자 묶음그룹이 달라 끊김
  • SQL 잡은 연산자 단위 지정이 없고 잡 전체 설정만 쓴다
  • 보통 무거운 연산자만 병렬도를 달리하거나, 병목을 지표로 나눠 볼 때 끊는다

실행 계획: 서브태스크로 펼치기

  • 실행 그래프
    • JobMaster가 잡 그래프를 병렬도만큼 펼쳐 실행 그래프(ExecutionGraph)를 만듦
  • 서브태스크
    • 실행 단위
    • 태스크 하나가 병렬도만큼 서브태스크로 복제됨
  • 키 그룹
    • keyBy 뒤 연산자는 키 그룹을 범위로 나눠 서브태스크마다 맡김
    • 키 그룹 = 해시(키) % max-parallelism (예: 128)
    • 같은 키는 항상 같은 키 그룹 → 같은 서브태스크로 감
    • 병렬도를 바꾸면 키 그룹 범위만 다시 나눔

자원 확보: 슬롯과 TM

왜 TM이 잡 그래프 다음에 뜨나
  • application 모드
    • TM 0개로 시작.
      • 필요한 슬롯 수가 나와야 TM 개수를 정할 수 있음
  • session 모드 · standalone
    • TM을 미리 띄워 두고, 잡이 오면 빈 슬롯에 배치
필요한 슬롯 = 가장 큰 병렬도  →  TM 수 = 필요한 슬롯 ÷ TM당 슬롯 (올림)
  1. JobMaster → ResourceManager: 슬롯 4개 요청
    • 슬롯 하나에 태스크별 서브태스크가 하나씩 같이 들어간다 (slot sharing)
    • 그래서 서브태스크 총수(6)가 아니라 가장 큰 병렬도(4)만큼 필요
  2. ResourceManager → 쿠버네티스: TM 파드 2개 요청
    • 빈 슬롯이 없으니 TM을 새로 띄운다
    • TM당 슬롯 = taskmanager.numberOfTaskSlots (여기선 2) → ⌈4 ÷ 2⌉ = 2개
  3. 쿠버네티스: TM 파드 생성
  4. TM → ResourceManager: 슬롯 2개씩 등록
    • 빈 슬롯 4개가 준비됨 → 다음 장에서 JobMaster가 서브태스크를 배치

TM 안을 확대하면: TM ⊃ 슬롯 ⊃ 서브태스크

  • TM은 파드 하나, JVM 프로세스 하나다.
    • 그 안을 numberOfTaskSlots개의 슬롯으로 나눈다
  • 슬롯은 서브태스크를 담는 자리다.
    • 슬롯 하나에 태스크마다 서브태스크가 하나씩 들어가서, 슬롯 하나가 소스부터 싱크까지 파이프라인 한 줄을 맡는 모양이 된다
  • 서브태스크는 스레드 하나로 돌고, 상태가 있으면 자기 상태 백엔드를 따로 갖는다.
    • 다른 서브태스크와 상태를 공유하지 않는다
  • 슬롯이 나누는 건 관리 메모리뿐이다.
    • JVM 힙과 CPU는 같은 TM의 슬롯끼리 같이 쓴다(격리 없음)

배치: 서브태스크를 슬롯에

  1. 배포
    • JobMaster가 받은 슬롯에 서브태스크를 배포
  2. 스레드
    • TM이 서브태스크마다 스레드를 띄워 실행
  3. 상태 백엔드
    • 상태가 있는 연산자의 서브태스크마다 하나씩 만듦
    • 체크포인트로 시작하면 여기서 상태를 복원
  4. 연결
    • 서브태스크끼리 데이터를 주고받을 버퍼와 연결을 만듦
    • 같은 TM이면 메모리로, 다른 TM이면 네트워크로 (그림의 점선)

한 장 요약

  1. 제출
    • FlinkDeployment 적용 → Operator가 JM 파드를 띄움
    • JM 안에서 main()이 돌아 잡 그래프가 되고 체이닝이 정해짐
  2. 실행 계획
    • JobMaster가 잡 그래프를 병렬도만큼 서브태스크로 펼침
  3. 자원 확보
    • 필요한 슬롯 = 가장 큰 병렬도
    • ResourceManager가 그만큼 TM 파드를 띄움
  4. 배치
    • 서브태스크가 슬롯에 배치되어 TM의 스레드로 실행
    • 상태는 서브태스크마다 자기 상태 백엔드에 둠
배치된 뒤 데이터가 흐르는 과정은 다음 문서 데이터 흐름에서 이어진다.
